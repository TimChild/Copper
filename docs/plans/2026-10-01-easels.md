# Easels

## The ask

The wiki app's wiki canvas (FigJam-style: stickies, frames, arrows, images, comments, presence)
inside Copper, shaped like Arc's Easels: a board you keep in the sidebar, drop tabs and
captures of pages onto, and share with other people who see it change live. Felipe builds the
cloud (sync, storage, auth, sharing); this plan is the browser/client side and the contract
between the two.

## What Arc's Easels were (and what we keep)

From Arc's release notes, help centre and the `arc.net/e` viewer bundle
(research notes beside the spikes):

- Introduced Dec 2021; still in Arc today (never cut — Arc itself went to maintenance mode in
  May 2025, and Notes were the thing removed in Apr 2024). FORK-PLAN's "dead in Arc" was wrong.
- Elements: text (a few font styles), shapes / arrows / freehand, images, links (YouTube, Vimeo,
  Twitch, Dailymotion play inline), and **web cards** = a Capture: `{url, image, favicon, text}`.
- **Capture**: ⇧⌘2 (or ⌘T › Capture), drag a rectangle; Edit / Retake; keeps its source link.
  **Live Capture** (Jul 2022, "experimental"): Play on a capture turns it into an interactive
  view of that rectangle, Pause puts the still back; ⌘R refreshes every live capture. Logged-in
  dashboards worked, so it used the viewer's own session. "Doesn't work with all websites."
- Lived as a pinned tab in a Space; ⌘T › New Easel; followed the Space's theme; pinch / ⌘± zoom,
  snap and alignment guides.
- Sharing: private / view-only / editable links, per-person editors, real-time presence cursors
  (Firestore underneath). Editing was Arc-for-Mac only; anyone could view at `arc.net/e/<id>`,
  where live captures fell back to their still picture.

Kept here: the capture gesture and shortcut, Play/Pause on a capture, ⌘R, easel-as-tab, the
three share levels, presence, stills for people who cannot render a live view. Added: the
wiki app board's stickies with live markdown, frames, comments and reactions, and frames for
the sites that allow them.

## Can a WebKit browser do it? Yes — and better than a web app can

The one thing a canvas in a web page cannot do is show most of the web. Measured in a plain
WKWebView (spike 1):

| in an `<iframe>` | |
|---|---|
| loads | Wikipedia, YouTube `/embed/`, example.com, anything that does not opt out |
| refused | GitHub (`frame-ancestors 'none'`), Google, Figma (`XFO: SAMEORIGIN`), X, Linear, NYTimes (`XFO: DENY`), Hacker News |

WebKit refuses those in the network process; Copper cannot strip the headers (no http(s)
interception in WKWebView) and should not try. Even where a frame loads, WebKit blocks
third-party cookies, so a framed app is never signed in.

Copper is not limited to iframes: it can put a **real top-level `WKWebView`** on the board.
Spike 2 placed a native web view as a subview of the canvas web view, moved and zoomed it from
a rect the canvas page posts on every camera move (`pageZoom` = camera zoom, so the page's
layout never changes), and a click at its centre landed in it. GitHub — refused as a frame —
rendered crisply at 1.6×. A top-level view uses the same `Store.websites` as the tab you
captured from, so it is signed in exactly as you are. `takeSnapshot` of an embed takes ~3.6 ms,
so refreshing several live captures a few times a second is cheap.

So every embed has two renderings, picked per site:

1. **Frame** — an `<iframe>` inside the canvas DOM. Free z-order, transforms, works in a web
   viewer too. Only for sites that allow framing.
2. **Native** — a `WKWebView` owned by Copper. Shown in the DOM as a snapshot image that
   refreshes while it is on screen ("live capture"); when you click into it the real view is
   laid over the placeholder so you can scroll, type and click; gestures on the board drop it
   back to the snapshot so panning never lags a frame behind.

The cost is the usual one for native-over-web: while an embed is active it sits above anything
on the board that overlaps it (stickies, other people's cursors). That is acceptable for the
one embed you are using and is why only the active embed is ever a live view.

## Architecture

```text
┌────────────────────────── Copper ──────────────────────────┐
│ Tab "copper-easel://<id>"   (sidebar row, pins, spaces,     │
│   WKWebView                  split, session restore: free)  │
│   └─ easel-web bundle  ── Yjs ── Hocuspocus ws ─────────────┼──▶ Felipe's cloud
│        canvas UI (from the wiki app)  ▲                      │     easel:<id> docs,
│        │ bridge: webkit.messageHandlers.easel               │     assets, members,
│        ▼                              │ ticket, assets       │     share links
│   EaselHost (Swift)  ── URLSession ───┴─────────────────────┼──▶ REST (bearer)
│     ├─ live embeds: pool of WKWebViews (Store.websites)     │
│     ├─ snapshots served back as copper-easel://snap/<shape> │
│     ├─ capture tool over any tab (region → embed)           │
│     └─ drag a tab / link onto the board                     │
└─────────────────────────────────────────────────────────────┘
```

### The canvas page: `easel-web/` (new, in this repo)

A Vite + React app built to a folder that `Package.swift` copies like `Fork/Backdrop`, served
from a `WKURLSchemeHandler` for `copper-easel://`. Spike 3: such a page is a secure context with
origin `copper-easel://<host>`, loads `<img>`s from the same handler, and opens `wss://` sockets. It is lifted from the
wiki app canvas rather than written fresh:

- **Lift as-is**: `canvas-doc` (minus its module-level singleton), `canvas-geometry`,
  `canvas-resize`, `canvas-layout`, `canvas-closed`, `canvas-comments`, `canvas-agents`,
  `text-diff`, `sticky-editor` + `sticky-markdown` (TipTap), `resize-handles`, `agent-cursors`.
- **Fork**: `wiki-canvas-page.tsx` (1.2k lines; page cards and the wiki drawer are wiki-only).
- **Adapter** for what the wiki app gets from its app: auth fetch (`sessionRequest` → the
  bridge), viewer `{id,name,color}`, toast, `navigate` (→ open a Copper tab), the few `@/ui`
  primitives and the `gw-*` Tailwind tokens.
- **Drop**: wiki page cards and search, canvas agent chat and hand-off (can come back later).

The Yjs schema stays a superset of `wiki:canvas` (`shapes` map, same field names) plus one new
shape type, so the wiki app's board and an easel can share renderers later. Copying now and
converging into a shared package later is deliberate: the wiki app's tree is shared with other
sessions and a push there is a Vercel deploy.

### The new shape: `embed`

Same `shapes` Y.Map entry as a sticky (`type, x, y, w, h, by`, last-writer-wins), plus:

| field | meaning |
|---|---|
| `url` | the page |
| `crop` | `{x, y, w, h}` in the page's CSS px; absent = top of the page |
| `layout` | the source tab's viewport width in CSS px (keeps desktop layouts; spike 2 showed a 500 px view gets GitHub's mobile site) |
| `mode` | `live` (keeps refreshing) or `still` (a picture taken once) |
| `render` | `frame` / `native`, decided on first load by whether the site allows framing, cached per origin |
| `snapshot` | asset id of the last picture **the author chose to share**, for people who cannot render it |
| `title`, `favicon` | for the card chrome |

Unknown types are dropped by the wiki app's `readShape`, so old clients ignore embeds rather than
break.

Each viewer renders a live embed **in their own browser with their own sign-in**: your
capture of a Linear board shows each person their own Linear. That is a feature for public
pages and the only safe default for private ones. The author's snapshot is uploaded only when
they ask ("Share a picture of this"), never automatically — otherwise a capture of an inbox
leaks it to everyone on the board.

### Native side (`Sources/Search/Fork/Easel/`)

- `Easel.swift` — the tab kind: recognises `copper-easel://<id>`, gives the tab a
  configuration with the scheme handler and the bridge; one-line hook in `Tab.swift`'s
  configuration choice and `Address.swift` (PATCHES.md rows).
- `EaselScheme.swift` — serves the bundle, and `copper-easel://snap/<shape>` images straight
  from memory (no base64 over the bridge).
- `EaselBridge.swift` — the JS ⇄ Swift messages below.
- `EmbedPool.swift` — at most N live `WKWebView`s (start at 6), shared data store, slept like
  tabs when off screen; refresh loop at 1–2 fps for visible live embeds, 0 when the easel tab
  is not frontmost; full-width view inside a clipping view sized to `crop`.
- `Capture.swift` — ⌘⇧2 on any tab: drag a rectangle, choose Live or Still, pick an easel
  (recent / new); records `url`, `crop` (view → CSS px via `pageZoom` and scroll), `layout`.
- Drag a sidebar row or a link onto an easel → `embed` at the drop point; paste a URL → same.
- ⌘K: New Easel, Open Easel…, Add Page to Easel.

### Bridge (JS ⇄ Swift), versioned

| from | message | |
|---|---|---|
| page | `ready {easelId}` | → native replies `config {docName, wsUrl, ticket, viewer}` |
| page | `ticket` | → fresh ticket (Hocuspocus `token: () => …` on every reconnect) |
| page | `embeds [{id, url, crop, layout, rect, z, visible}]` | rAF-throttled on camera move |
| page | `activate {id}` / `deactivate {id}` | lay the real view over / back to picture |
| page | `open {url}` | open a Copper tab |
| page | `upload {name, mime, bytes}` | native uploads with the bearer, returns asset id |
| native | `snap {id, version}` | page bumps `<img src=copper-easel://snap/id?v=…>` |
| native | `insert {embed…, at}` | from capture / drop / ⌘K |
| native | `frameable {origin, ok}` | result of the first frame attempt |

Native talks to the cloud's REST API with URLSession (no CORS); the page talks to the cloud only
over the Yjs websocket.

## Contract for Felipe (the cloud side)

What the client needs, in the order it is needed. Names are proposals; any backend works.

1. **Auth.** Copper already holds a per-app personal token (`fxb_…`, agent.json) for linked
   agents apps. Needed: `POST /v1/easels/:id/ticket` (bearer) →
   `{ticket, wsUrl, docName, expiresAt, viewer:{id,name,color}, role}`; the ticket is checked
   per document (Hocuspocus `onAuthenticate`), not only at the upgrade.
   Today the wiki app mints 60 s HMAC tickets only behind a session cookie, and `fxb_` tokens
   belong to a different service — so this is a new route either way.
2. **Easels.** `GET /v1/easels` → `[{id, title, role, updatedAt, thumbnail}]`;
   `POST /v1/easels {title}`; `PATCH`; `DELETE`.
3. **Sync.** Hocuspocus documents `easel:<id>` with persistence (the wiki app's `YDoc` table works;
   its name regex and the one-board limit would need to go). Read-only role enforced server-side.
4. **Assets.** `POST /v1/easels/:id/assets` (raw bytes + Content-Type) → `{id}`;
   `GET /v1/easels/:id/assets/:asset` with the bearer (native fetches and serves it to the page
   through the scheme handler). Images today live in Postgres; fine to start.
5. **Sharing.** Members with roles (owner / editor / viewer), invite by email, and a share link
   (view or edit). The wiki app's workspace allowlist is two emails, so "we all share it" needs real
   per-easel membership.
6. **Later, optional.** A web viewer at `https://…/e/<id>` that renders the same doc (embeds show
   as frames where allowed, else the shared snapshot); MCP/agent tools for easels (Felipe owns
   Copper's agent side already).

Until the cloud exists the client runs against `easel-web/dev/stub-server.mjs`: a local
Hocuspocus plus the five routes above in memory, so two Copper windows (or Copper and a
browser) can be multiplayer on day one.

## Phases (client)

| phase | ships | done when |
|---|---|---|
| P0 | spikes (done) | framing table, native overlay + snapshot timing in `research/…/spike` |
| P1 | `copper-easel://` tab with the lifted canvas, local-only doc | stickies, frames, arrows, images, pan/zoom work in a Copper tab; restored after relaunch |
| P2 | `embed` shape: frame + native rendering, drag a tab on, paste a URL | GitHub + Wikipedia + YouTube on one board, interactive on click, snapshot during gestures |
| P3 | capture tool (⌘⇧2), live vs still | a cropped region of a signed-in page stays live on the board |
| P4 | multiplayer against the stub, then Felipe's cloud | two Macs see each other's cursors and edits; share sheet; easels in ⌘K |
| P5 | polish | thumbnails in the sidebar row, embed pool tuning, offline queue, templates |

## Risks

- **Many live embeds = many web processes.** Cap the pool, sleep off-screen embeds, pictures
  for the rest.
- **Native-over-web z-order** for the active embed (above). Arc's live captures had the same
  shape of trade-off.
- **Privacy** of shared pictures (above): explicit, per embed.
- **Usage.** Reviewers called Arc's Easels unpolished next to FigJam, and authoring was Mac-only.
  The bet here is a board you share with the people (and agents) you work with, on the
  wiki app canvas that already has the editing depth Arc's lacked.
